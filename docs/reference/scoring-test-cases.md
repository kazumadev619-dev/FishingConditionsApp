# スコア計算のテストケース表

> - **状態**: 記録（仕様ではない。仕様の正は [scoring-algorithm.md](./scoring-algorithm.md)）
> - **対象**: `src/lib/scoring/`、`src/lib/utils/scoreRank.ts`（[testing-policy.md](../guides/testing-policy.md) 7節②のうち、純粋な計算の部分）
> - **作成**: 2026-11-22（[#426](https://github.com/kazumadev619-dev/FishingConditionsApp/issues/426)）。突き合わせた時点の develop は `7d1970d`

スコア計算の入力ごとに、同値クラスと境界値を洗い出し、既存のテストで確かめられているかを突き合わせた表。期待値の出どころは、すべて [scoring-algorithm.md](./scoring-algorithm.md)（仕様（正））の節で、実装の式や出力は写していない（[testing-policy.md](../guides/testing-policy.md) 4節）。

この表は、テストを足したり消したりしたときに更新する。表の「テスト」列は、`ファイル名 › describe の名前` で書く。

## 読み方

- 同値クラス: 同じ点数になる入力の範囲。1つの代表値で確かめる。点数が時間や高さの一次式で変わる区間（潮汐タイミングなど）は、同じ点数にならないので同値クラスにならない。整数の時間だけでなく、小数の時間でも式を確かめる。
- 境界値: 点数が変わる境目。境目ちょうどと、そのすぐ外を確かめる。
- 「テスト」列が「なし」の行は、仕様に期待値がないため、テストを書かない行（理由を「出どころ」に書く）。

## 1. 潮汐スコア（0〜40点）

入力: 現在時刻（JST）、当日の満潮・干潮の時刻と高さ（cm）。式は 潮汐タイミング（0〜25）+ 潮の大きさ（0〜15）。

### 1.1 潮汐タイミング

極値（満潮・干潮の両方）のうち、現在時刻に最も近いものまでの時間 h（時間）で決まる。出どころ: 「潮汐タイミング評価」（h ≦ 2 で 25 − 6.25h、2 < h ≦ 4 で 12.5 − 6.25(h − 2)、それ以外は 0）。

| 同値クラス・境界値 | 入力（極値 12:00 に対する現在時刻） | 期待値 | テスト |
|---|---|---|---|
| 極値ちょうど | 12:00 | 25 | `tideScore.test.ts › 潮汐タイミング`（12:00） |
| 2時間以内（後） | 13:00 | 18.75 | 同上（13:00） |
| 0〜2時間の小数の時間（一次式） | 12:30 / 13:30 / 10:45 | 21.875 / 15.625 / 17.1875 | 同上（小数の時間。#431 のレビューで追加） |
| 2時間ちょうど（前・後） | 10:00 / 14:00 | 12.5 | 同上（10:00、14:00） |
| 2時間超〜4時間以内 | 15:00 | 6.25 | 同上（15:00） |
| 2〜4時間の小数の時間（一次式） | 14:30 / 08:30 | 9.375 / 3.125 | 同上（小数の時間。#431 のレビューで追加） |
| 4時間ちょうど | 16:00 | 0 | 同上（16:00） |

## 5. 足したテスト（#426）

仕様と実装の食い違いは見つからなかった。足したのは、表の穴を埋めるテストで、いずれも `tideScore.test.ts`。

- 潮位差が負のとき 5 点（「0.5m 未満」の表）
- 最も近い極値が配列の先頭にあるときも、近いほうを選ぶ
- 複数日のデータから当日だけを使う

PR #431 の独立レビュー（レビュー役の別エージェント。Opus）が提案し、実装者が取り込んだ反証テストが、次の2点である。期待値は、仕様の式と表から決めた。実装の誤りは見つからなかった（いまの実装で通る）。

- 潮汐タイミングを、小数の時間（12:30、13:30、10:45、14:30、08:30）でも確かめる（一次式であることを守る）
- 最も近い満潮・干潮を、現在より後ろ・前の両方から選ぶ

## 6. 変異テスト

[`mutation-test`](../../.claude/skills/mutation-test/SKILL.md) で、スコア計算の実装を60通りに壊し、`npx vitest run src/lib/scoring src/lib/utils/scoreRank.test.ts` で確かめた（対象: `tideScore.ts`、`weatherScore.ts`、`timeScore.ts`、`index.ts`、`scoreRank.ts`）。

- 57件が落ちた（KILLED）。
- 3件が通った（SURVIVED）。いずれも、仕様の上で値が変わらない変異である。
  - 潮汐の2時間の境目 `<= 2` → `< 2`（ちょうど 2 時間で、どちらの式も 12.5）
  - 潮汐の4時間の境目 `<= 4` → `< 4`（ちょうど 4 時間で、どちらの式も 0）
  - 最も良い要素の比較 `>` → `>=`（同点のときだけ変わり、同点の扱いは仕様にない）

PR #431 のレビューを受けて、5通りを足して確かめた（計65通り）。

- 4件が落ちた。0〜2時間・2〜4時間のタイミングを段階式にする変異、最も近い極値を現在より後ろ・前から優先して選ぶ変異。足したテストの前は、0〜2時間を段階式にする変異と、後ろを優先する変異が通っていた。
- 1件が通った。最も悪い要素の比較 `<` → `<=` は、最も良い要素と同じく、同点のときだけ変わる（同値）。したがって、生き残りは計4件で、すべて同値である。
## 7. カバレッジの記録

[ADR-009](../adr/009-testing-quality-policy.md) の決定（カバレッジの閾値もツールも置かない）は変えない。依存を足さずに、一度だけ測った記録である。網羅率は、コードが実行されたかどうかを示すだけで、結果を確かめたかどうかは示さない（[testing-policy.md](../guides/testing-policy.md) 8節）。
