# 主要 API の応答時間のベースライン（2026-11-22）

Issue: #427。対象は、課金される上流を呼ぶ 4 ルート（`/api/scores`、`/api/conditions/tide`、`/api/weather`、`/api/locations/search`）。`Server-Timing`（#111・#112）の `dur` を根拠に、ボトルネックの有無と、ある場合の箇所を調べた。

## 結論

- **アプリ内の処理（Redis・計算・DB）にボトルネックは見つからなかった。** 1 接続での `Server-Timing` の中央値は、キャッシュありで 0.7〜1.1 ms、キャッシュなしで 2〜5 ms（上流の待ちを除く）。
- **キャッシュミスのときの応答時間は、上流の待ちでほぼ決まる。** 上流の待ちを 200 ms にすると、`tide`・`weather`・`locations-search` は約 210 ms、`scores` は約 420 ms になった。
- **`scores` は、天気と潮汐の上流を順番に呼んでいる**（`src/app/api/scores/route.ts` の `computeScore`）。ミスのときの時間が、2 つの上流の待ちの合計になる。#432 に切り出した。
- **キャッシュが空のキーに同時に来た要求は、要求の数だけ上流を呼ぶ。** 同じキーへの 10 件の同時要求で、上流の呼び出しは 10 回（`scores` は天気 10 回 + 潮汐 10 回）だった。上流のクォータを使う。#433 に切り出した。
- 絶対値は、この環境（Mac の Docker）のもの。Raspberry Pi の値ではない（「限界」を参照）。

## 条件

| 条件 | 内容 |
|---|---|
| 床（`floor`） | `/api/weather?lat=x&lon=y`。入力検証で 400 になる。認証とレート制限の判定だけを通る |
| キャッシュあり（`cached`） | 同じパラメータを繰り返す。1 回目（測定に入れない）でキャッシュに載せる |
| キャッシュなし（`uncached`） | 要求ごとに別のパラメータ（座標・港コード・検索語）。毎回ミスになり、上流（スタブ）を呼ぶ |
| 上流の遅延 | スタブの応答を 0 ms または 200 ms 遅らせる。0 ms でアプリ側の処理、200 ms で上流の待ちの積み上がりを見る |
| 同時接続数（VUS） | キャッシュあり: 1・10・50。キャッシュなし: 1・10。各条件 20 秒 |

集計に入れるのは、期待する状態コード（`floor` は 400、そのほかは 200）の応答だけ。それ以外（429 など）は件数だけ数える。今回の測定では、期待以外の応答は 0 件だった。また、全応答に `Server-Timing` が付いていた。

### スタブの前提

- 上流の遅延の 200 ms は想定値で、実際の遅さではない。参考に、tide736 を 1 回だけ呼んだときの応答は 0.21 秒だった（1 回の値で、ばらつきは分からない）
- 潮汐の応答の形と大きさは、その 1 回の実物（`rg=week`: 7 日分、1 日 73 点、約 52 KB）に合わせた。天気・検索の応答は、アプリの整形が読む項目だけの最小の形で、実物より小さい。この 2 つの JSON の解析時間は実物より短い側にずれる

## ボトルネックの切り分け

`Server-Timing` は経路ごとの合計 1 つなので、条件を変えた測定の差で内訳を出した。1 接続の中央値（ms）。

| 対象 | 床 | キャッシュあり | ミス（上流 0 ms） | ミス（上流 200 ms） |
|---|---|---|---|---|
| `scores` | 0.7 | 0.7 | 4.5 | 419.0 |
| `tide` | 0.7 | 1.1 | 3.3 | 210.8 |
| `weather` | 0.7 | 0.8 | 2.2 | 208.1 |
| `locations-search` | 0.7 | 0.7 | 2.2 | 208.0 |

1. **認証とレート制限（床）**: 0.7 ms。キャッシュありの経路（0.7〜1.1 ms）のほとんどは、これで説明できる。Redis の読み出しとルート固有の処理は、0.0〜0.4 ms ほどしか上乗せしない
2. **ミスのアプリ側の処理**（ミス 0 ms − キャッシュあり）: `scores` 3.8、`tide` 2.2、`weather` 1.4、`locations-search` 1.5。上流クライアント・整形・Redis への書き込み・計算の合計で、小さい
3. **上流の待ち**（ミス 200 ms − ミス 0 ms）: `tide`・`weather`・`locations-search` は約 207 ms（遅延 200 ms + 7 ms ほど）。`scores` は 414.5 ms で、約 2 倍。天気と潮汐を順番に呼ぶためで、並べて呼べば約 210 ms になる計算
4. **DB**: 対象の経路は DB を使わない（接続できない宛先でも、全部 200 / 400 で返った）
5. **負荷をかけたとき**: 50 接続のキャッシュありは、`floor` も `scores` も `weather` も `locations-search` も約 900〜1000 件/秒で頭打ちになり、`Server-Timing` の中央値が約 22 ms に伸びた。床（認証とレート制限だけ）が同じ上限なので、共通部分と Node の 1 プロセスが上限を決めている。ルート固有の処理が支配しているわけではない。例外は `tide` で、約 520 件/秒、p95 110 ms と半分の水準だった。キャッシュに載った 52 KB の JSON の読み出しと応答の組み立てが、1 件あたり約 1 ms 余分にかかる

### 判断

- 想定の負荷（1 ユーザーあたり 60 回/分まで）に対して、アプリ内の処理は十分に小さい。改善が要るボトルネックではない
- 応答が遅くなるのは、キャッシュミスで上流を待つときだけ。ミスの頻度は TTL（天気 30 分、潮汐 6 時間、スコア 30 分、検索 1 時間）で決まる
- ミスのときに、`scores` の待ちが上流 2 回ぶんになること（#432）と、同時の初回要求が重複して上流を呼ぶこと（#433）は、構造上の無駄として残る
- `tide` のキャッシュありの 52 KB は、今の負荷では問題にならないので issue にしない。リクエストの増加や `range=month` の利用が増えたら見直す

## 限界

- Mac の Docker での値。Pi（Arm、CPU が遅い）では、アプリ側の処理の絶対値が大きくなる。Pi での測定は、本番に近い環境への負荷になるので、この作業では行っていない
- 上流の遅延は想定値。実際の OpenWeatherMap・Google の遅さとばらつきは測っていない
- 各条件 1 回 20 秒。ばらつきの評価（繰り返し）はしていない。差が数 ms の比較は目安として読む
- k6 とアプリが同じ Docker VM の CPU を使うので、50 接続の上限は、アプリ単体の上限より低い可能性がある
- ブラウザ側（描画、ネットワーク）と、Cloudflare Tunnel を通る時間は含まない

## 再現手順

前提: Docker。k6 のインストールは要らない。リポジトリのルートで実行する。

```bash
# 1. 環境を起動する（runner イメージのビルドを含む）
docker compose -f scripts/perf/docker-compose.yml -p fishing-perf up -d --build

# 2. 1 条件を測る: <対象> <条件> [VUS] [DURATION か ITERATIONS=N] [上流の遅延 ms]
#    対象: floor | scores | tide | weather | locations   条件: cached | uncached
scripts/perf/run.sh scores uncached 10 30s 200

# 3. 全条件を流す（約 12 分）。結果は scripts/perf/out/results.jsonl
scripts/perf/matrix.sh 20s
node scripts/perf/table.mjs scripts/perf/out/results.jsonl

# 4. 同時の初回要求（キャッシュを温めない）
WARMUP=0 scripts/perf/run.sh scores cached 10 ITERATIONS=10 200

# 5. 片付け
docker compose -f scripts/perf/docker-compose.yml -p fishing-perf down
```

- `run.sh` は、条件ごとにこの環境の Redis を空にする。ほかの Redis には触れない
- アプリのコードは変えない。外部 API への `fetch` を、`NODE_OPTIONS=--import` で読み込む `redirect-upstream.mjs` が、スタブへ向け替える。向け替え対象以外の外部ホストへの `fetch` は、その場で失敗させる
- k6 のスクリプトは、同時接続数・時間・条件・上流の遅延を環境変数で受け取る（`scripts/perf/k6.js` の冒頭）
