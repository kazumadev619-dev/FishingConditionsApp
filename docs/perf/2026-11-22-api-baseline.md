# 主要 API の応答時間のベースライン（2026-11-22）

Issue: #427。対象は、課金される上流を呼ぶ 4 ルート（`/api/scores`、`/api/conditions/tide`、`/api/weather`、`/api/locations/search`）。`Server-Timing`（#111・#112）の `dur` を根拠に、ボトルネックの有無と、ある場合の箇所を調べた。

## 結論

- **ハンドラ内の処理（Redis・計算・DB）にボトルネックは見つからなかった。** 1 接続での `Server-Timing` の中央値は、キャッシュありで 0.6〜1.0 ms、キャッシュなしで 2.5〜4.8 ms（上流の待ちを除く）。ハンドラの外（`proxy.ts` での認証）は `Server-Timing` に入らない。50 接続では、応答時間の半分ほどがそこで使われている（「ボトルネックの切り分け」の 5）。
- **キャッシュミスのときの応答時間は、上流の待ちでほぼ決まる。** 上流の待ちを 200 ms にすると、`tide`・`weather`・`locations-search` は約 210 ms、`scores` は約 420 ms になった。
- **`scores` は、天気と潮汐の上流を順番に呼んでいる**（`src/app/api/scores/route.ts` の `computeScore`）。ミスのときの時間が、2 つの上流の待ちの合計になる。#432 に切り出した。
- **キャッシュが空のキーに同時に来た要求は、要求の数だけ上流を呼ぶ。** 同じキーへの 10 件の同時要求で、上流の呼び出しは 10 回（`scores` は天気 10 回 + 潮汐 10 回）だった。上流のクォータを使う。#433 に切り出した。
- 上の値は、ローカル（Mac の Docker、上流はスタブ）のもの。Pi 本番を負荷を絞って測ると、ハンドラ内の処理は約 4〜6 倍かかったが、それでも 1 件 4〜6 ms で、結論は変わらない。応答時間の大半は、Cloudflare と Tunnel 経由の往復（約 255 ms）だった。実際の上流の遅さは 35〜93 ms で、想定の 200 ms より小さく、#432 の効果は「約 210 ms の短縮」ではなく約 35 ms と見積もり直した（「Pi 本番の実測と、外部 API の実際の遅さ」）。

## 条件

| 条件 | 内容 |
|---|---|
| 床（`floor`） | `/api/weather?lat=x&lon=y`。入力検証で 400 になる。認証とレート制限の判定だけを通る |
| キャッシュあり（`cached`） | 同じパラメータを繰り返す。1 回目（測定に入れない）でキャッシュに載せる |
| キャッシュなし（`uncached`） | 要求ごとに別のパラメータ（座標・港コード・検索語）。毎回ミスになり、上流（スタブ）を呼ぶ |
| 上流の遅延 | スタブの応答を 0 ms または 200 ms 遅らせる。0 ms でアプリ側の処理、200 ms で上流の待ちの積み上がりを見る |
| 同時接続数（VUS） | キャッシュあり: 1・10・50。キャッシュなし: 1・10。各条件 20 秒 |

集計に入れるのは、期待する状態コード（`floor` は 400、そのほかは 200）の応答だけ。それ以外（429 など）は件数だけ数える。今回の測定では、期待以外の応答は 0 件だった。また、全応答に `Server-Timing` が付いていた。

最初の条件がプロセスの温め（JIT・ルートの初回読み込み）に左右されないよう、`matrix.sh` は先に、結果に入れない温め（各ルート 10 接続で 5 秒）を流す。全条件を 2 回流し（約 12 分ずつ）、2 回目を下の表に載せる。

### スタブの前提

- 上流の遅延の 200 ms は想定値で、実際の遅さではない。参考に、tide736 を 1 回だけ呼んだときの応答は 0.21 秒だった（1 回の値で、ばらつきは分からない）
- 潮汐の応答の形と大きさは、その 1 回の実物（`rg=week`: 7 日分、1 日 73 点、約 52 KB）に合わせた。天気・検索の応答は、アプリの整形が読む項目だけの最小の形で、実物より小さい。この 2 つの JSON の解析時間は実物より短い側にずれる

## ボトルネックの切り分け

`Server-Timing` は経路ごとの合計 1 つなので、条件を変えた測定の差で内訳を出した。1 接続の中央値（ms、2 回目。1 回目との差は 1 ms 以内で、`tide` のキャッシュありだけ 1.5 対 1.0）。

| 対象 | 床 | キャッシュあり | ミス（上流 0 ms） | ミス（上流 200 ms） |
|---|---|---|---|---|
| `scores` | 0.9 | 1.0 | 4.8 | 420.4 |
| `tide` | 0.9 | 1.0 | 3.7 | 212.3 |
| `weather` | 0.9 | 0.6 | 2.5 | 208.7 |
| `locations-search` | 0.9 | 0.8 | 2.6 | 209.4 |

1. **ハンドラ内の認証とレート制限（床）**: 0.9 ms。キャッシュありの経路（0.6〜1.0 ms）は、床とほぼ同じ。Redis の読み出しとルート固有の処理は、1 ms の中に収まる
2. **ミスのアプリ側の処理**（ミス 0 ms − キャッシュあり）: `scores` 3.8、`tide` 2.7、`weather` 1.9、`locations-search` 1.8。上流クライアント・整形・計算と、Redis への書き込みの開始（JSON 化）の合計で、小さい。`withCache` は書き込みの完了を待たない（`src/lib/cache/helpers.ts`）ので、書き込みの待ちは `Server-Timing` に入らない
3. **上流の待ち**（ミス 200 ms − ミス 0 ms）: `tide` 208.6、`weather` 206.2、`locations-search` 206.8（遅延 200 ms + 7 ms ほど）。`scores` は 415.6 で、約 2 倍。天気と潮汐を順番に呼ぶためで、並べて呼べば約 210 ms になる計算
4. **DB**: 対象の経路は DB を使わない（接続できない宛先でも、全部 200 / 400 で返った）
5. **ハンドラの外（`proxy.ts`）**: 50 接続では、k6 の応答時間の中央値が `Server-Timing` の約 2 倍になる（floor で 98.6 ms 対 47.4 ms、weather で 91.3 ms 対 42.2 ms）。差の中身は測っていないが、コードと応答から次のように読んでいる。`proxy.ts` が要求ごとに `auth()` を呼び、セッション JWT の復号と、`Set-Cookie`（`authjs.session-token`・`authjs.csrf-token`・`authjs.callback-url` の 3 つ）の付与を行う。ハンドラの `withUserRateLimit` でも `auth()` をもう一度呼ぶ。この `proxy.ts` ぶんは `Server-Timing` に入らない。1 接続では k6 と `Server-Timing` の差は 1.5〜2 ms で、負荷が上がると待ち行列で伸びる
6. **負荷をかけたとき**: 50 接続のキャッシュありは、温めたあとは `floor`・`scores`・`weather`・`locations-search` がどれも同じ水準（2 回とも約 450〜510 件/秒）で頭打ちになった。床（認証とレート制限だけ）が同じ上限なので、共通部分と Node の 1 プロセスが上限を決めている。共通部分の主な中身は、5 の認証（`proxy.ts` とハンドラの 2 回の `auth()`）だと推定している（プロファイルは取っていない）。ルート固有の処理が支配しているわけではない。例外は `tide` で、同じ回の中でほかのルートの約 0.7 倍（332〜359 件/秒）だった。キャッシュに載るのは tide736 の生の応答（約 52 KB）ではなく整形後の値で、`range=week` では約 28 KB（Redis の `STRLEN` で 28,288 バイト、応答の本文は 28,340 バイト）。この大きさの JSON の読み出しと応答の組み立てで、1 件あたりの CPU が増えるためと見ている

### 判断

- 想定の負荷（1 ユーザーあたり 60 回/分まで）に対して、ハンドラ内の処理は十分に小さい。改善が要るボトルネックではない。「ボトルネックなし」はハンドラ内（`Server-Timing` の範囲）についての判断で、ハンドラの外の認証については、想定の負荷では問題にならないと見ているが、重い負荷での上限の中身は未調査
- 応答が遅くなるのは、キャッシュミスで上流を待つときだけ。ミスの頻度は TTL（天気 30 分、潮汐 6 時間、スコア 30 分、検索 1 時間）で決まる
- ミスのときに、`scores` の待ちが上流 2 回ぶんになること（#432）と、同時の初回要求が重複して上流を呼ぶこと（#433）は、構造上の無駄として残る
- `tide` のキャッシュありは、今の負荷では問題にならないので issue にしない。リクエストの増加や `range=month` の利用が増えたら見直す

## Pi 本番の実測と、外部 API の実際の遅さ

オーナーの指示のもとで、Raspberry Pi 上の本番（https://fishing.kazuma-lab.com）を、負荷を絞って測った。経路は、Mac → Cloudflare → Tunnel → Pi。測定用のセッション Cookie はオーナーが用意したもので、値はこの文書にもログにも出していない（測定後にオーナーが破棄する）。

### 計画と実績

| 項目 | 内容 |
|---|---|
| スクリプト | `scripts/perf/prod-probe.mjs`（k6 は使わず、間隔を置いた逐次の要求） |
| 同時接続 | 1 または 2。ユーザー × ルートのレート制限（60 回/分）に当たらないよう、1 接続は 2 秒間隔、2 接続は 3 秒間隔（毎分 40 回以下） |

| キャッシュありの `Server-Timing` | 0.6〜1.0 ms | 3.9〜6.2 ms（約 4〜6 倍） |
| キャッシュあり・2 接続でのばらつき | — | ほぼ変わらない（3.8〜5.9 ms） |
| 全体の応答時間 | k6 で `Server-Timing` + 1〜2 ms | 約 260〜275 ms（`Server-Timing` の約 60 倍） |
| 上流の待ち（想定値 200 ms） | 200 ms を入れた | 実際は 35〜93 ms（Mac から）。Pi のミスは weather 約 90 ms、locations 約 149 ms |

- Pi のハンドラ内の処理は、ローカルの約 4〜6 倍かかる（Arm の CPU が遅いため）。それでも 1 件 4〜6 ms で、想定の負荷（1 ユーザー 60 回/分まで）では問題にならない
- 応答時間の大半は、ネットワークの往復（Cloudflare と Tunnel 経由で約 255 ms）。`Server-Timing` の外にある
- 負荷は絞ったので、Pi の上限の件数/秒は測っていない（測るとほかのユーザーに影響しうるため、行っていない）

### 結論は変わるか

- **変わらない:** ハンドラ内に、改善が要るボトルネックはない。ミスは上流の待ちが支配する。ただし、Pi では上限（件数/秒）は未測定なので、「想定の負荷では問題ない」という範囲での結論
- **変わる点（見積もり）:** 上流の実際の遅さは、想定の 200 ms より小さい（35〜93 ms）。#432（`scores` の天気と潮汐を並べて呼ぶ）の効果は、「約 420 ms → 約 210 ms」の見込みではなく、実際の遅さ（天気 約 93 ms、潮汐 約 35 ms）では、直列の約 128 ms が並列の約 93 ms になる程度、つまり約 35 ms（約 3 割）の短縮になる。無駄の構造は変わらないが、体感への効果は小さい。#432 の優先度は、この数字で見直すとよい
- **変わらない:** #433（同時の初回要求の重複呼び出し）は、応答時間ではなく上流のクォータの問題なので、遅さの実測には影響されない

## 限界

- ローカルの表は Mac の Docker での値。Pi では、ハンドラ内の処理が約 4〜6 倍かかる（上の「Pi 本番の実測」）。Pi は負荷を絞って測ったので、Pi の件数/秒の上限は未測定
- ローカルの測定の上流の遅延 200 ms は想定値。実際の遅さは、Mac から各 5 回測った（35〜93 ms）。Pi から見た値と、時間帯によるばらつきは測っていない
- 各条件 20 秒で、全条件を 2 回流した。件数/秒は回によって約 2 倍ぶれるので、絶対値は使わず、同じ回の中の相対値だけを比べる。差が数 ms の比較は目安として読む
- k6 とアプリが同じ Docker VM の CPU を使うので、50 接続の上限は、アプリ単体の上限より低い可能性がある
- k6 は要求ごとに新しい `CookieJar` を使う（Cookie を持ち越さない）。そのため、毎回が初回の訪問として扱われ、csrf の Cookie も毎回作られる。ブラウザより共通部分の負荷が重く出る可能性がある
- 実行時間の異常（Mac のスリープなど）は、`table.mjs` の ⚠ で気づける。レビュー時の再測定では、Docker の VM が止まって 1 条件が 612 秒かかった例があった（測り直すと 20 秒で、値は正常だった）
- ローカルの表には、ブラウザ側（描画、ネットワーク）と、Cloudflare Tunnel を通る時間は含まない（Pi の実測の「全体」には Cloudflare と Tunnel の往復が含まれる）

## 再現手順

前提: Docker と Node（`npm ci` 済みのリポジトリのルート）。Cookie の生成（`make-cookies.mjs`）がホストの Node で `next-auth/jwt` を読む。k6 のインストールは要らない。以下は、リポジトリのルートで実行する。

```bash
# 1. 環境を起動する（runner イメージのビルドを含む）
docker compose -f scripts/perf/docker-compose.yml -p fishing-perf up -d --build

# 2. 1 条件を測る: <対象> <条件> [VUS] [DURATION か ITERATIONS=N] [上流の遅延 ms]
#    対象: floor | scores | tide | weather | locations   条件: cached | uncached
scripts/perf/run.sh scores uncached 10 30s 200

# 3. 全条件を流す（約 12 分。先に温めを流す）。結果は scripts/perf/out/results.jsonl に追記される
#    測り直すときは、先に out/results.jsonl を消す。Mac は、測っている間にスリープさせない（caffeinate -i など）
scripts/perf/matrix.sh 20s
node scripts/perf/table.mjs scripts/perf/out/results.jsonl

# 4. 同時の初回要求（キャッシュを温めない）
WARMUP=0 scripts/perf/run.sh scores cached 10 ITERATIONS=10 200

# 5. 本番（Pi）を絞って測る（オーナーの許可があるときだけ。Cookie はファイルに「名前=値」を 1 行で置き、権限は 600。値は出力されない）
PERF_COOKIE_FILE=<ファイル> node scripts/perf/prod-probe.mjs https://fishing.kazuma-lab.com authed

# 6. 外部 API の実際の遅さ（キーを持つ env ファイルを指定。各 5 回）
npx dotenv -e <env ファイル> -- node scripts/perf/upstream-latency.mjs 5 1000

# 7. 片付け
docker compose -f scripts/perf/docker-compose.yml -p fishing-perf down
```

- `run.sh` は、条件ごとにこの環境の Redis を空にする。ほかの Redis には触れない。k6 が失敗したら（TARGET の綴り間違い、warm-up の失敗など）、終了コード 1 で止まる
- Linux では未確認。`make-cookies.mjs` は `out/cookies.json` を権限 600 で書くが、`grafana/k6` は別のユーザー（uid 12345）で動くので、バインドマウントした環境では読めない可能性がある。Mac の Docker Desktop では問題にならなかった。読めないときは、`out/cookies.json` を `chmod 644` する
- アプリのコードは変えない。外部 API への `fetch` を、`NODE_OPTIONS=--import` で読み込む `redirect-upstream.mjs` が、スタブへ向け替える。向け替え対象以外の外部ホストへの `fetch` は、その場で失敗させる
- k6 のスクリプトは、同時接続数・時間・条件・上流の遅延を環境変数で受け取る（`scripts/perf/k6.js` の冒頭）
