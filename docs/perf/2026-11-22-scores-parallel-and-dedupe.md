## #432: `/api/scores` のミスで、天気と潮汐を並べて呼ぶ

`scripts/perf/run.sh scores uncached <接続数> 20s 200` を、接続数ごとに 3 回ずつ。

| 接続数 | 直す前の `Server-Timing` 中央値（3 回） | 直した後（3 回） | 直す前の k6 応答の中央値 | 直した後 |
|---|---|---|---|---|
| 1 | 424.1 / 418.5 / 422.3 ms | 214.7 / 216.3 / 213.6 ms | 437 / 428 / 432 ms | 225 / 227 / 224 ms |
| 10 | 445.5 / 448.7 / 452.9 ms | 236.2 / 239.9 / 237.2 ms | 472 / 472 / 476 ms | 259 / 263 / 259 ms |

- 上流の遅延 200 ms の約 2 回ぶんが、約 1 回ぶんになった（1 接続でほぼ半分）
- 同じ 20 秒の間の完了件数は、1 接続で 46〜47 件から 88〜89 件になった
- ベースラインの「外部 API の実際の遅さ」（Mac から実際の上流を各 5 回測った値。Pi からではない）で、実際の上流の遅さは 35〜93 ms だった（[ベースライン](./2026-11-22-api-baseline.md)）。想定の 200 ms より小さいので、本番での短縮は、この表の約 210 ms ではなく約 35 ms と見積もっている

## #433: キャッシュが空のキーへの同時要求で、上流を重複して呼ばない

`WARMUP=0 scripts/perf/run.sh <tide|scores> cached 10 ITERATIONS=10 200`。キャッシュを空にして、10 接続から同じキーに 10 件を同時に送る。直した後は 3 回測った。スタブが数えた上流の呼び出し回数は次のとおり。

| 対象 | 直す前 | 直した後（3 回とも同じ） |
|---|---|---|
| `/api/conditions/tide` | 潮汐 10 回 | 潮汐 1 回 |
| `/api/scores` | 天気 10 回 + 潮汐 10 回 | 天気 1 回 + 潮汐 1 回 |

応答時間（`Server-Timing` の平均）は、上流の待ちが同じ 200 ms なので変わらない（`tide` は約 240 ms から 229〜261 ms、`scores` は約 469 ms から 436〜444 ms）。減るのは、応答時間ではなく、上流の呼び出し（クォータ・課金）である。

## 限界

- 直す前後とも、Mac の Docker で、上流をスタブにした値。件数/秒は回によって約 2 倍ぶれるので、絶対値は使わず、同じ条件の前後の比べだけを読む
- Pod が複数のときの #433 の効果は測っていない（本番は `replicas: 1`）
