# ADR-010: `docs/reference/` を仕様の正にする

**日付:** 2026-11-07
**ステータス:** 採用済み

## 決定

仕様の正は `docs/reference/` に置く。実装が仕様の文書と違うときは、文書を直さない限り、実装の誤りとして扱う。

- 仕様を変える PR は、同じ PR で、文書とテストの期待値も更新する。
- `docs/reference/` の各文書の冒頭に、`状態`（仕様（正）／説明（参考））、`対応する実装`、`最終確認` を書く。「仕様（正）」は、テストの期待値の出どころになる次の4つで、残りは「説明（参考）」とする。参考の文書は、実装と違うときは実装が優先される。
  - `scoring-algorithm.md`、`authentication.md`、`api-error-handling.md`、`api-integration.md`
- 仕様に触れる変更を含む昇格の前に、別のエージェントが、文書と実装を突き合わせる。
- 文書から実装やテストを生成する仕組みは作らない。

## 理由

### 1. 期待値の出どころが、文書なのに、文書を直す規則がなかった

[ADR-009](./009-testing-quality-policy.md) とポリシーの4節は、テストの期待値を仕様（issue、ADR、`docs/reference/`）から決めると定めている。一方で、実装を変えたら文書も直す、という規則は、`CLAUDE.md`、`docs/README.md`、`docs/guides/`、`issue-delivery` のどこにもなかった。片側だけが決まっていた。

### 2. 実際に、文書が取り残された

[#357](https://github.com/kazumadev619-dev/FishingConditionsApp/issues/357) の精査で、次の食い違いが見つかった。

- 429: #317 が 429 をリトライ対象から外したが、`api-error-handling.md` は 429 をリトライ対象のままだった。
- `/auth/*`: #116 が前方一致を完全一致に変えたが、`authentication.md` は「`/auth/*` 許可」のままだった。
- 天気スコア: 文書と実装は、初版（#51）から一致していなかった。風速・気圧・天候の段階と、潮位差の定義が違う。実装は一度も変わっていない。

どれも、実装を直した PR が文書に触れなかった（または、最初から写し損ねた）ことが原因である。

### 3. 実装を正にしなかった

実装を正にすると、テストの期待値が実装の出力の写しになり、誤っていても Green になる（ポリシー1節）。文書が実装に引きずられて古くなるのは、規則で防ぐ。

### 4. 実装が正しいと分かっているものは、文書を直す

「文書が正」は、文書の中身が正しいことを意味しない。429 と `/auth/*` は、実装に意図を示すコメントがあり、文書が古かっただけなので、文書を直した。天気スコアと潮位差は、実装の閾値が本番で使われてきたので、実装を維持して文書を書き直し、ユーザーが釣りの感覚として妥当かを確認して承認する（[#367](https://github.com/kazumadev619-dev/FishingConditionsApp/issues/367)）。承認した表が、テストの期待値の出どころになる。

## 代替案

### 実装を正にし、文書は説明にする（不採用）

上の3。

### 仕様の表を、機械で読める形（JSON や TS の定数）にして、文書とテストと実装が同じものを参照する（不採用）

文書から実装を生成する作りになり、このリポジトリの規模に比べて重い。ズレは、文書から決めたテストと、昇格前の突合で拾う。

### 文書の更新を CI で強制する（今回は見送り）

文書の変更を、対応する実装の変更と結びつけて検査する方法が、まだ見つかっていない。PR テンプレートのチェックと、人のレビューで運用する。ポリシーの強制を CI に移す [#355](https://github.com/kazumadev619-dev/FishingConditionsApp/issues/355) と同じ扱いにする。

## 結果

- 各文書の冒頭に、状態・対応する実装・最終確認を書く。まだ突き合わせていないので、最終確認は「未確認」で始める。突き合わせは [#370](https://github.com/kazumadev619-dev/FishingConditionsApp/issues/370) で行う。
- PR テンプレート（`.github/pull_request_template.md`）に、「仕様に触れたか／触れたなら文書とテストの期待値を更新したか」のチェックを入れる。
- `github-push-pr` は、PR 本文をテンプレートから作る。`issue-delivery` の昇格の手順に、突合を足す（`.claude/skills/` と `.agents/skills/` の両方）。
- `docs/README.md` の `reference/` の説明に、仕様の正であることを書く。
- 429 と `/auth/*` の文書は、[#368](https://github.com/kazumadev619-dev/FishingConditionsApp/issues/368) で直した。天気スコアと潮位差は #367 で扱う。

## 補足: この決定を見直すべきタイミング

- 文書と実装を結びつけて検査する方法が見つかったとき（CI での強制）。
- 「仕様（正）」の文書に、期待値の出どころとして使われない文書が混ざっていると分かったとき。`api-integration.md` は「使用予定 API」の見出しで始まっており、仕様として使えるかを #370 で確かめる。
