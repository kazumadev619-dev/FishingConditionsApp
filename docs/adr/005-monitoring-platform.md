# ADR-005: 監視基盤は Grafana Cloud 無料枠とし、Pi には Alloy だけを置く

**日付:** 2026-10-17
**ステータス:** 採用済み（実装は #280）

## 決定

本番（Raspberry Pi 5 上の k3s 1台）の監視は、Grafana Cloud の無料枠で行う。Pi には収集エージェントの Alloy だけを置く。

| 項目 | 決定 |
|------|------|
| Alloy の導入 | 公式 Helm チャート k8s-monitoring を手動で `helm install` する。values はリポジトリに置き、Grafana Cloud のトークンは SOPS で暗号化する |
| 収集対象 | メトリクス（Prometheus）、ログ（Loki。Pod の stdout）、トレース（Tempo）、ブラウザ（Faro） |
| アプリの計測 | `instrumentation.ts` で OpenTelemetry を有効にし、Alloy に OTLP で送る。トレースは 100% 送る |
| DB（Neon） | postgres_exporter は入れない。クエリの時間はトレース、接続プールはアプリのメトリクスで見る |
| 長期の傾向 | 14日までは OTel のカウンター。それより長い推移は Grafana の PostgreSQL データソースで Neon を直接集計する（読み取り専用ロール、自動更新なし） |
| Redis | redis_exporter を入れる |
| Faro | 匿名のセッション ID だけを送り、ユーザー ID やメールアドレスは送らない |
| アラート | Slack の監視専用チャンネルに送る。データが5分届かない／5xx の割合が5分で 5% 超え／外部 API のエラー率が10分で 20% 超え／Grafana Cloud の使用量が無料枠の 80% 超え |

## 理由

### 1. Pi が落ちたことに気づけるのはクラウドだけ（決め手）

本番は Pi 1台である。監視を同じ Pi に立てると、Pi が落ちたときに監視も一緒に落ち、肝心の障害に気づけない。Grafana Cloud なら「データが届かない」こと自体を検知して通知できる。

### 2. Pi の資源を食わない

kube-prometheus-stack を自前で立てると、Prometheus と Grafana で 1〜2GB のメモリを使い、TSDB の書き込みで SD カードも傷む。Alloy だけなら 100〜200MB 程度で済む。

### 3. データを手元に置く理由が薄い

DB はすでに Neon（クラウド）にある。監視データだけを手元に残しても、得るものが少ない。

### 4. Faro（ブラウザの計測）をそのまま受けられる

Web Vitals とブラウザの例外（#247）を受けるには、インターネットに公開された受け口が要る。Grafana Cloud には Faro の受け口があり、自前で公開する手間が無い。

### 5. postgres_exporter は Neon を眠らせなくする

Neon は無料枠の compute 時間に上限があり、アイドル時は autosuspend で止まる。postgres_exporter が定期的に問い合わせると compute が止まらなくなり、過去に起きた Neon の枯渇（503）を自分で再現してしまう。Grafana から Neon を集計するパネルも、自動更新を切って「開いたときだけ」起きるようにする。

## 代替案

### Pi の k3s に kube-prometheus-stack を自前で立てる（不採用）

保持期間や系列数の制限が無く、外部にも依存しない。しかし理由 1 と 2 の欠点が大きい。

### メトリクスだけを集める（不採用）

最小構成ではある。しかしブラウザの例外に気づけない問題（#247）が残る。ログとトレースは無料枠に収まる見込みなので、最初から集める。

### 利用イベントを記録するテーブルを DB に作る（保留）

保持期間を気にせず、利用状況の推移を細かく取れる。ただしスキーマの変更が要る。既存のテーブル（users、user_favorites など）では見たい傾向が取れないとわかったら検討する。

### Neon の消費量を API で取り込む（保留）

1日1回の取得なら Neon を起こす回数は少ない。Neon のコンソールで足りないとわかったら追加する。

## 結果

- Grafana Cloud の保持期間は 14日。14日を超える傾向は、Neon を直接集計するパネルでしか見られない
- 無料枠には上限がある（アクティブな系列 1万本など。正確な値は #282 で実測して確かめる）。k8s のメトリクスは絞って取り込み、使用量が 80% を超えたら通知する
- 監視データは Grafana Labs に送られる。ブラウザからは個人と結びつく情報を送らない
- Alloy は手動の `helm install` なので、GitHub Actions のデプロイには乗らない。手順は `docs/guides/monitoring.md` に書く

## 補足: この決定を見直すべきタイミング

- 無料枠の上限に恒常的に当たるようになったとき（有料プランにするか、自前に移すかを比べる）
- 本番が Pi 1台でなくなり、監視を別のノードに置けるようになったとき
- 14日より長い期間のメトリクスを、日常的に見たくなったとき
