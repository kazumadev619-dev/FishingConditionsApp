# テスト品質ポリシー

テストを書くとき、直すとき、レビューするときに従う方針。人も AI も同じものを読む。決めた理由は [ADR-009](../adr/009-testing-quality-policy.md) にある。テストランナーの選定は [ADR-003](../adr/003-testing-strategy.md)、置き場所とコマンドは [development.md](./development.md#テスト戦略) にある。

参考にした記事は次の2本である。
- [AIが実装し、AIがテストし、AIが「問題ありません」と言う時代の品質保証](https://qiita.com/y0us91/items/2feffd2cc6c672717973)（Qiita）
- [良いテストを書き、良いテストを見分ける](https://zenn.dev/nexta_/articles/unit-testing-principles-essence)（Zenn）

## 1. 目的

テストが Green であることは、ソフトウェアが正しいことの証明ではない。Green が示すのは、いま存在するテストについて、観測した結果が期待値と一致したことだけである。実装とテストを同じ作り手（AI を含む）が書くと、期待値が実装と同じ誤解から作られ、誤っていても Green になる。

そこで次の2点を守る。

1. テストの期待値は、実装ではなく仕様から決める。
2. 実装を壊したら落ちるテストだけを残し、内部の作りに結びついたテスト（整理しただけで赤くなるテスト）を増やさない。

### 用語

Zenn は「1つの振る舞いを、速く、ほかのテストから隔離して確かめるものを単体テストと呼び、そのどれかを満たさないテストをすべて統合テストと呼びます」と定義している。この定義では、画面から通す E2E テストも統合テストに含まれる。

ADR-003 は、モックを使う Route Handler のテストを「統合テスト」（Stage 2）と呼んでいる。Zenn の定義では、これは単体テストに当たる。このガイドで「統合テスト」と書くときは、Zenn の定義に従う。ADR-003 の Stage の名前とは食い違うが、ADR-003 は書き換えない。

## 2. 良いテストの4本柱

| 柱 | 問い |
|---|---|
| 退行に対する保護 | 実装を壊したら赤くなるか |
| リファクタリングへの耐性 | 振る舞いを変えず中身を整理しても、通り続けるか |
| 迅速なフィードバック | すぐ終わり、すぐ結果が分かるか |
| 保守のしやすさ | 意図が読みやすく、準備が少ないか |

4つは掛け算で考える。どれか1つがゼロなら、そのテストの価値もゼロである。最初の3つは同時に最大化できないので、**リファクタリングへの耐性を手放さない**ことを優先する。誤報（壊れていないのに赤くなる）が続くと、本物の失敗も無視されるためである。

## 3. 兆候チェックリスト

テストを書いたとき、直したとき、レビューするときに確かめる。

#### 誤報の兆候（整理しただけで赤くなる）
- [ ] private のメソッドや値、内部の呼び出し回数を検証していないか。回数や「呼ばれないこと」が仕様なら検証してよい（5節の「回数の例外」）。その場合は、テスト名かコメントに仕様を書く（4節）。
- [ ] 取得だけの処理を、呼び出し回数まで含めてモックしていないか（スタブで値を返すだけにする）。

#### 見逃しの兆候（実装が壊れても緑のまま）
- [ ] 緑になる理由が、実装ではなく、テストが用意したスタブの戻り値になっていないか。
- [ ] 何を渡されても通る書き方（`expect.any(String)` だけ、`toBeDefined()` だけ）になっていないか。
- [ ] 期待値が、実装と同じ計算式や、いまの実装の出力値から作られていないか（4節）。
- [ ] モックの既定の戻り値で、準備していない呼び出しが黙って通っていないか。

#### 守る価値がない兆候
- [ ] 値を受け渡すだけの、壊れようのない処理をなぞっていないか。
- [ ] 網羅率のためだけに、結果をほとんど確かめないテストを足していないか。

この確認で見つけたものの扱い: 誤報を繰り返すテストや、何も確かめないテストは、直すか消す。既存のテストは、変更するときに直す（9節）。

このチェックリストが見るのは、書いてあるテストの質である。書かれていない分岐は拾えないので、高リスク箇所では `mutation-test`（7節）で補う。

### 例

良い例（`src/lib/utils/dashboardUtils.test.ts`）: 固定の時刻 `2026-10-16T20:48:27Z` を、タイムゾーンを3種類に変えても `05:48`（JST）になることを確かめる。期待値は「この時刻は JST で 10/17 05:48」という仕様から決めた値で、実装の式を写していない。

兆候の例は、`src/lib/actions.test.ts` に2つある。
- `redirect` のスタブが、遷移先を持たない固定の `Error('NEXT_REDIRECT')` を投げる。`/login` と `/dashboard` のどちらへ遷移しても同じ失敗になるので、遷移先が仕様であるテストでは、遷移先を区別できない（5節の `redirect`）。
- 入力の誤りの結果を `expect.any(String)` で確かめている。何の文字列でも通る。

## 4. 期待値の出どころ

新しいテストの期待値は、仕様から決めた値にする。仕様とは、issue、ADR、`docs/reference/` の文書、外部仕様書を指す。実装の式を写した値（実装と同じ計算を、テストの中でもう一度書く）と、いまの実装の出力をそのまま貼った値は使わない。いまの実装にバグがあっても、期待値がそれを正しいと固定してしまうためである。

期待値の出どころは、テスト名かコメントから分かるようにする（issue 番号、ADR、文書名）。レビューで、仕様から決めた値か、実装の定数を写した値かを見分けるためである。ログやメッセージの期待値は、実装が使う関数（`maskEmail` など）で作らず、`'ow***@example.com'` のようなリテラルにする。

仕様に根拠が見つからないときは、テストを書く前にユーザーへ確認する。落ちたテストを通すために期待値を書き換える前も同じである（実装の誤りを先に疑う）。

## 5. テスト・ダブルの分類表

モック（呼ばれ方を検証する）は、外へ出ていく副作用に限る。スタブ（値を返すだけ）は、原則として呼び出し回数を検証しない。例外は、表のあとの「回数の例外」にまとめる。

| 対象 | 扱い |
|---|---|
| `resend`、外部への送信（メール、通知） | モック。送った中身まで検証する。 |
| OpenWeather・tide736・Google Maps など取得系の外部 API | スタブ。呼び出し回数は原則検証しない。回数が課金・クォータ・キャッシュの仕様なら検証する（`src/lib/cache/serviceCacheIntegration.test.ts`）。 |
| `logger` | ログの内容が仕様のときだけ検証する。 |
| `redirect`（`next/navigation`） | 遷移先を持つ例外を投げるスタブにし、`rejects` で遷移先を検証する。 |
| `auth()`、`headers()` | スタブ。戻り値で状態（ログイン済みか、ヘッダの値）を作る。 |
| `bcrypt` | 実物を使う。hash は約50ms なので、コストは変えない。compare の入力は、テストの中で低いコストで作ったハッシュにしてよい。期待値は「`bcrypt.compare(元のパスワード, 保存値)` が真を返す」。スタブにするなら結果だけを固定し、ハッシュ文字列は検証しない。コストの高い処理を避けることが仕様のテスト（入力の誤りでは計算しない、など）は、スタブにして「呼ばれないこと」を検証してよい（回数の例外）。 |
| Prisma（暫定規則） | 読み取りはスタブ。書き込み（create、update、updateMany、createMany、delete、deleteMany、`$transaction`）は引数を検証してよい。回数の固定（1回だけ呼ばれる）は、二重に書かれないことが仕様のときだけにする。ドライバの挙動は `src/lib/prismaConstraints.test.ts` と同じく、採取した固定値で持つ。 |
| Redis（`ioredis`）（暫定規則） | スタブまたは偽サーバ（`src/lib/cache/client.unresponsive.test.ts` の方式）。書き込み（increment、set）はキーと TTL を検証してよい（`src/lib/rateLimit.test.ts`。運用でキーを走査するので、キーの形は前提になる）。 |
| 自前のモジュール（`@/lib/email`、`@/lib/rateLimit`、`@/auth` など）をモックするとき | そのモジュールが包む外部の行に従う（`@/lib/email` は送信の行、`@/lib/rateLimit` は Redis の行、`@/auth` の `signIn` は `auth()` の行）。引数と戻り値の約束は実物に合わせ、戻り値を準備しない `vi.fn()` の `undefined` で分岐が変わらないようにする（成功と失敗の両方の経路を通す）。クラスを差し替えるときは、実物を継承するか `importOriginal` で実物を引く。 |

### 回数の例外

Zenn は、スタブを何回呼んだかは内部の作りなので確かめない、としている。ここでの例外は、このリポジトリ独自のもので、**回数そのもの、または「呼ばれないこと」が仕様になっている場合**に限る。

- 課金・クォータ・キャッシュ（上流を何回呼ぶか。`src/lib/cache/serviceCacheIntegration.test.ts`）
- 二重実行の禁止（二重に書かれない、二重に送られない）
- コストの高い処理を避ける（入力の誤りでは `bcrypt` を計算しない、など）
- 副作用が起きないこと自体が仕様（上限に達したら、ユーザーを作らず、メールも送らない）

例外にするときは、テスト名かコメントに、その仕様を書く。

### 暫定規則

Zenn は、自アプリだけが使う DB はモックにせず、実DBの統合テストで確かめるとしている。いまの CI（`.github/workflows/ci.yml`）には Postgres も Redis もないので、実DBを使うテストは1つもない。そのため、Prisma と Redis の扱いは上の暫定規則にしている。

解除の条件: CI に Postgres と Redis が入り、実DBを使うテストの基盤ができたとき（[#354](https://github.com/kazumadev619-dev/FishingConditionsApp/issues/354)）。解除したら、Prisma と Redis は実物で確かめる。

## 6. 判断の切り出し

業務の判断（条件分岐、計算）と I/O（DB、外部 API）が1つの関数に混ざっていて、テストにスタブや DB が要るときは、判断に必要な値を引数で受け取る純粋関数に切り出す。入力と結果だけで確かめられる形（出力値を見るテスト）が、最も質が高い。残った I/O の部分は薄くし、要所だけを統合テストで守る。

- 切り出す前に、いまの振る舞いを固定するテストを置く。 振る舞いが変わっていないことを確かめる安全網がないと、整理は安全に進まない。
- 実DBのない間（暫定規則の間）、安全網が確かめるのは、戻り値、遷移先、外へ出る副作用（送ったメールの中身など）だけにする。Prisma の書き込みの引数は、切り出しの作業で落ちるので、安全網にしない。DB と絡んだ判断の切り出しは、暫定規則の解除（[#354](https://github.com/kazumadev619-dev/FishingConditionsApp/issues/354)）の後に行う。
- 切り出すことと、内部を晒すことは違う。 テストしやすくするために、private の値や内部状態を外から触れるようにしない。
- 切り出しにも引き換えがある（判断の途中でもう一度データを読む場合など）。どこまで分けるかを考えること自体が設計である。

## 7. 高リスク箇所

次の箇所は、壊れたときの影響が大きく、壊れたことに気づきにくい。要件は、テストではなく実装側のパスがここに当たるかどうかで決まる。

| 役割 | パス |
|---|---|
| ① 認証・認可 | `src/auth/`、`src/proxy.ts`、`src/lib/actions.ts`、`src/lib/googleSignIn.ts`、`src/lib/token.ts`、`src/lib/email.ts`、`src/app/api/auth/`、`src/app/api/favorites/`（所有者の確認に関わる変更。一覧の取得だけの変更は対象外）、`src/lib/csp.mjs` |
| ② スコア計算 | `src/lib/scoring/`、`src/lib/scoringService.ts`、`src/lib/tideService.ts` |
| ③ データ移行・シード | `prisma/migrations/`、`prisma/seed.ts`、`prisma/data/`、`scripts/verify-seed-rerun.sh` |
| ④ 入力検証・レート制限 | `src/lib/validators/`、`src/lib/password-validation.ts`、`src/lib/rateLimit.ts`、`src/lib/prismaConstraints.ts` |

見直しの時期: [#354](https://github.com/kazumadev619-dev/FishingConditionsApp/issues/354)（実DB基盤）が完了したときと、この4つの役割を持つファイルを、一覧の外に新しく作ったとき。

### 追加の要件

PR で次を行う。

- ①②④（認証・認可、スコア計算、入力検証・レート制限）: [`mutation-test`](../../.claude/skills/mutation-test/SKILL.md) の結果を PR 本文に載せる。実装とは別のエージェントが、間違いを証明するテストを差分として提案し、実装者が取り込み、誰が書いたかを PR 本文に書く。提案は fork には頼まず、仕様と差分だけを渡した新しいエージェント（できれば別モデル）に頼む（実装者の文脈を引き継ぐと、同じ見落としを共有する）。
- ③: `bash scripts/verify-seed-rerun.sh`（使い捨てのコンテナで seed を再実行する）の結果を載せる。このスクリプトは、空の DB に `migrate deploy` を流してから seed を再実行するので、マイグレーションの変更もこれで確かめられる。`prisma/migrations/` に冪等性は求めず、`psql -f` で手で流さない。マイグレーションは `_prisma_migrations` で多重適用を防いでおり、手で流すと壊れる行がある。
- すべて: issue か PR に、守る状態（何が壊れたら困るか）を書く。
- 反証テストが落ちたら、実装を直す。期待値の根拠が仕様に見つからなければ、テストを書き換える前にユーザーへ確認する。
- GitHub Actions 版の AI factory（ADR-007。まだマージされていない）の PR は、Bash が使えず `mutation-test` を流せない。移行後、高リスク箇所に触れる場合は、マージ前に人か Claude が流して、結果を PR に追記する。

この要件は PR テンプレート（`github-push-pr` の「テスト計画」）と人のレビューで確かめる。CI での強制は [#355](https://github.com/kazumadev619-dev/FishingConditionsApp/issues/355) で扱う。

## 8. カバレッジ

網羅率は、コードが実行されたかどうかを示すだけで、結果を確かめたかどうかを示さない。このリポジトリでは、閾値を置かず、計測のツールも入れない。薄い箇所を探す目安として使いたいときは、手元で `vitest run --coverage` を試してよい（依存を足さないと動かない）。テストが退行を検知できるかは、網羅率ではなく、[`mutation-test`](../../.claude/skills/mutation-test/SKILL.md) で確かめる。

## 9. 適用範囲

- このガイドが適用されるのは、新しく書くテストと、変更するテストである。リファクタで誤報により落ちた既存のテストを直す場合も、変更に含める。
- 既存のテストの見直しは、[#353](https://github.com/kazumadev619-dev/FishingConditionsApp/issues/353) で扱う。
- `src/lib/validators/` のようにテストが1つもないディレクトリへ新しくテストを書くときも、このガイドに従う。
