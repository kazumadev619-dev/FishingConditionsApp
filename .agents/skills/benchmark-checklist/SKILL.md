# benchmark-checklist

> **参考元:** [pstack `benchmark-checklist`](https://github.com/cursor/plugins/tree/main/pstack/skills/benchmark-checklist)

「速くなった」「重くなった」という主張を、**再現可能で偏りのない実測証拠**で裏打ちするための検証チェックリスト。計測スクリプトの配置は `scripts/perf/`、記録の決まりは [`docs/perf/README.md`](../../../docs/perf/README.md) に従う。

## 報告前に必ず実測で答える 7 つの質問

数値を PR や `docs/perf/` に書く前に、次の 7 問すべてにコマンド結果・実測値で答える。1 つでも根拠が欠けていれば「改善した」と断定しない。

| # | 質問 | このリポジトリでの確認ポイント |
|---|---|---|
| **1** | **律速点（Limiter）は何か？（なぜ 2 倍速くならないか）** | `Server-Timing`（`src/lib/serverTiming.ts`）やログ内訳で、CPU・DB・Redis・上流 API 待ち・直列実行のどれが支配的かを特定する |
| **2** | **本番相当の条件で測ったか？** | `next dev` ではなく `next build` + `next start`（または本番相当コンテナ）。キャッシュ状態（cold / warm）、DB 件数、上流スタブ（`scripts/perf/stub.mjs`）の遅延設定を明記する |
| **3** | **再現性はあるか？** | ウォームアップを除外したうえで複数回測り、ベースラインと変更後を **交互（A → B → A → B）** に実行する。平均だけでなく **中央値（p50）・p95・ばらつき（最小〜最大）** を出す |
| **4** | **エラー・非 2xx・タイムアウトを数えているか？** | 401・429・500・タイムアウトで即返却された失敗リクエストが「高速化」に紛れていないか、ステータスコード別の件数を明示する |
| **5** | **本来の仕事が本当に実行されたか？** | 空配列の返却、フォールバック、キャッシュ誤ヒット、処理スキップで速く見えていないか。レスポンスの件数・中身が期待どおりであることを確認する |
| **6** | **実利用に即したワークロードか？** | 同時接続数、リクエストの偏り（同一地点への同時アクセスなど）、認証 Cookie の有無が実際の利用条件と合っているか |
| **7** | **ベースラインとの比較は公正か？** | 同じマシン・同じ負荷状態・同じデータとスタブ条件・明記した commit（`git rev-parse --short HEAD`）同士で比べているか |

## 記録の決まり（[`docs/perf/README.md`](../../../docs/perf/README.md) 準拠）

- ファイル名は `docs/perf/YYYY-MM-DD-<題>.md` にする
- 冒頭に **日付・commit・環境・負荷・上流の扱い** を必ず書く
- **過去の記録ファイルは書き換えない。** 再計測したら新しい日付のファイルを追加し、[`docs/README.md`](../../../docs/README.md) の索引に載せる

## 出力の形（PR 本文・`docs/perf/` 共通チェック）

```markdown
## ベンチマーク検証（benchmark-checklist）

- 対象 commit: `<base>` vs `<head>`
- 条件: <起動モード / DB・Redis・上流スタブ条件 / 負荷 / 実行回数（交互）>

| 指標 | ベースライン（p50 / p95） | 変更後（p50 / p95） | 差分 | エラー件数（非 2xx） |
|---|---|---|---|---|

### 7 問の確認
1. 律速点: <Server-Timing 等の内訳>
2. 本番相当性: <build+start / キャッシュ状態>
3. 再現性: <交互実行の回数とばらつき>
4. エラー計上: <2xx / 非 2xx / timeout 件数>
5. 実処理の確認: <レスポンス中身・件数の確認結果>
6. ワークロード妥当性: <実利用との対応>
7. 比較の公正さ: <同一環境・同一データ・残る制約>
```
