# merge-readiness

PR をマージしてよいかを、**コードを変えない**レビュー役が判定する。直すのは実装者、マージはオーナー。この skill の外にある。

**PR コメントと追記コメントは、調整役がオーナーとして書く。** 判定役は文案を報告に添えるだけで、GitHub には投稿しない（`pr-verifier` の約束、AGENTS.md の「投稿は明示承認のあと」）。

ほかの文書が持つことは写さずリンクする。テストの基準は [`docs/guides/testing-policy.md`](../../../docs/guides/testing-policy.md)、仕様の扱いは [ADR-010](../../../docs/adr/010-spec-source-of-truth.md)、検証役の約束（コミットも push もしない、など）と PR の取り込みは [`pr-verifier`](../../agents/pr-verifier.md)。

## 守ること

- **シークレットの値を読まない・出さない。** 差分やログに混ざっていたら、再掲せず「混入あり」とファイル名・キー名だけを報告する（止める条件 7）
- 別のエージェントに頼むときも、同じ制約を指示する
- 判定した head の SHA を必ず控える（止める条件 6、やり直しの決まり）

## 判定は3段階

| 判定 | 意味 | 再レビュー |
|---|---|---|
| マージしてよい | 止める条件なし。指摘は無し、または直さなくてよい低だけ | 不要 |
| 小さな修正のあとマージしてよい | 止める条件なし。直してほしい低がある（直せば足りる） | 不要 |
| 要修正 | 高・中の指摘がある、または止める条件に当たる | 直したあとにやり直す |

## マージを止める 7 条件

どれか 1 つでも当たれば「要修正」。

1. CI が未通過、または develop と衝突している
2. 正しさの指摘が中以上
3. issue の完了条件が未達（先送りの理由が書かれていない）
4. `docs/reference/` の「仕様（正）」との食い違い、または更新漏れ（ADR-010）
5. テスト品質ポリシー違反（壊しても落ちない、など。[testing-policy.md](../../../docs/guides/testing-policy.md) 3〜5節）
6. 判定した head と、いまの head が違う
7. シークレットの混入

過剰設計と好みは止める条件ではない。低として報告するだけ。

## 指摘の重さ

| 重さ | 例 |
|---|---|
| 高 | 本番の不具合、データ損失、セキュリティ、仕様違反 |
| 中 | 特定の条件で壊れる、完了条件の一部が欠ける、壊れても落ちないテスト |
| 低 | 読みやすさ、重複、過剰設計、書き足し |

## 手順

1. **取り込む。** 手順は [`test-review`](../test-review/SKILL.md) の「取り込む」と `pr-verifier` に従う。ただし、すでに専用の worktree にいるなら別の一時 worktree は作らず、その中で PR の head に合わせる。develop が head の祖先でなければ `git merge origin/develop` で重ねる（push しない）。`npm ci` し、`gh pr view` で head の SHA を控える
2. **手元で回す。**
   - `npm run check-code` は必ず
   - 壊して落ちるかの確認（[`mutation-test`](../mutation-test/SKILL.md)）は、テストを足した・変えた PR だけ
   - E2E・build は、変更が関係するときだけ
   - 共通基盤・認証・DB スキーマ・3リポジトリ契約に触る PR では、[`blast-radius`](../blast-radius/SKILL.md) の観点（diff 外の急所が実行で裏取りされているか）を確かめる
   - 性能改善を主張する PR では、[`benchmark-checklist`](../benchmark-checklist/SKILL.md) の 7 問が実測で満たされているかを確かめる
3. **計画と照合する。** 計画・決定がある issue は、項目を表にして「合う・一部・合わない」を書く（必須）。計画・決定のありかは依頼する側が渡す。渡されなければ issue と PR 本文から探し、見つからなければ完了条件だけと照合したと報告に書く。「合わない」「一部」の項目には、中身に応じて重さを付ける（決定に反するなら中以上）
4. **ほかの skill を使う。**
   - `ponytail:ponytail-review` と testing-policy を、この判定の中で使う
   - `mattpocock-skills:code-review` と OCR（`open-code-review:delegate-review`）は、観点だけ取り込む。サブエージェントは起こさない
   - 大きな PR（`src` の変更が 300 行以上、または CI・認証・DB に触る）だけ、Antigravity による突合が要る。判定役は「突合が要る」と報告に書くところまで。依頼文は調整役が作り、仕様と差分と手順だけを渡す（先の結論は渡さない）
5. **ほかの開いている PR を見る。** 消えるファイルへのリンク、同じ箇所の変更。マージの順番への注意として書く。止める条件ではない
6. **PR のラベル・担当者（Assignees）・マイルストーンが埋まっているか見る。** 決まりは [`github-push-pr`](../github-push-pr/SKILL.md) に従う。埋まっていなければ低の指摘（止める条件ではない）
7. **head を確かめ直す。** 報告を書く直前に `gh pr view` で head を見て、控えた SHA と同じか確かめる（止める条件 6）
8. **後始末。** 一時 worktree を作ったなら消し、`git status` が clean であることを確かめる

## 報告（全文をチャットに出し、PR 番号入りのファイルにも書く）

結論 1 行 → 指摘 → 確かめたこと の順。ファイルの置き場所は依頼文で指定された場所。なければ scratchpad の `reports/`。

```markdown
## PR #<番号>: <判定>（head `<SHA>`）

### 指摘
| 重さ | 場所 | 問題 | 直し方 |
|---|---|---|---|
| 高/中/低 | <ファイル:行> | <何が起きるか> | <どう直すか> |

（無ければ「なし」）

### 計画・完了条件との照合
| 計画・決定 | 判定（合う / 一部 / 合わない） |
|---|---|

### 確かめたこと
- 実行したもの: <check-code、変異テスト、E2E など。件数と結果>
- 確かめていないこと: <範囲。コード読みだけの箇所を「確認した」と書かない>
- ほかの開いている PR との関係: <マージの順番の注意。無ければ「なし」>
```

## PR コメント

マージ可と決まったら、調整役がオーナーとして PR にコメントを残す。判定役は、次の形で文案を報告に添える。書くのは判断の理由であり、報告の転記ではない。社内の評価制度には触れない。

```markdown
## レビュー結果: <マージしてよい / 小さな修正のあとマージしてよい>（head `<SHA>`）

### 判断の理由
<計画との照合の表、または完了条件ごとの判定>

### レビュー後に直したこと（`<旧SHA>` → `<新SHA>`）
1. <直したこと>

### 残した点（マージは止めない）
- <低の指摘、確かめていないこと>
```

## やり直しの決まり

- **head が変わったら、判定は無効。**
- 指摘どおりの修正か、develop の取り込みだけなら、判定役をもう一度立てず、調整役が差分と CI を確かめて、追記コメントで判定を引き継ぐ（`## 追記: head <SHA> でもマージしてよい`。変わったことと、前の判断が変わらない理由を書く）
- `src` の挙動が変わる修正なら、レビューをやり直す
