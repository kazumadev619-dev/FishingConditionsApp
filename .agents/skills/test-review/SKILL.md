# test-review

`docs/guides/testing-policy.md` は、テストを**書くとき**の方針である。この skill は、書かれたあとのテストを**別のエージェントや人が検証する**手順を定める。Green は正しさの証明ではないので、実装を壊して落ちることと、守ると言った状態に穴がないことを、実行して確かめる。

何をどの文書が持つか（ADR-009）:
- 検証役の約束（コミットも push もしない、シークレットを出さない、など）と PR の取り込み手順は、`pr-verifier`（`.claude/agents/pr-verifier.md`、Codex は `.codex/agents/pr-verifier.toml`）に従う。ここには書かない
- 変異の入れ方と spec の仕様は、[`mutation-test`](../mutation-test/SKILL.md) に従う
- 兆候・期待値・モックの基準は `docs/guides/testing-policy.md`（3〜5節）。高リスク箇所の追加要件は 7節。網羅率は根拠にしない（8節）

## 手順

### 1. 取り込む

worktree の中にいなければ `git worktree add --detach <一時パス> origin/<headRefName>` で作り、そこに `cd` する。そのあと `pr-verifier` の手順 0〜1 に従い、次を流す。終わったら `git worktree remove --force <一時パス>`。

```bash
npm ci
git merge --no-edit origin/develop   # PR 上の CI は古い develop の上で走っている。一時 worktree のマージコミットは push しないので構わない
npx vitest run <関連ディレクトリ> --reporter=verbose && npm run type-check
```

PR で足したテストの名前が、出力にすべてあることを確かめる（`it.skip` や include 外のファイルは、緑でも何も検証していない）。

### 2. 何を保証するテストか

追加・変更されたテストごとに、守っている振る舞いを **1 行**で書く。PR 本文と、根拠の issue・仕様と突き合わせ、期待値の根拠がテスト名かコメントから辿れるかを見る。高リスク箇所（7節）なら、PR 本文に追加要件の掲載物（①②④ は `mutation-test` の結果と反証テストの出典、③ は `scripts/verify-seed-rerun.sh` の結果）があるかも確かめる。

### 3. 変異テスト

`mutation-test` の spec にまとめて流す。**PR 本文の変異テストの結果は、そのまま信じず再実行する。**

- 検証する worktree に `cd` してから流す（適用先は `mutation-test` の spec の表のとおり）
- **関連するテスト全体（ディレクトリ単位）で流す。** 1 ファイルだけで「生き残った」に見えた変異を、別のテストが落とすことがある（#377: 潮汐の「分を無視する」変異を、`timeZone.test.ts` が落とした）
- **生き残った変異は、等価なものとテストの穴に分け、根拠を書く。** 等価の例: 満点が 15+12+8=35 のとき、上限 35→36 は結果が変わらない。穴なら、落とす入力を 1 つ書く

| 観点 | 例 |
|---|---|
| 確実に落ちる | テストが直接読む値を壊す（ハーネスの確認） |
| 境界値・比較演算子 | しきい値の「ちょうど」「直上」「直下」、`<=` と `<` |
| 点数・定数 | 各点数を 1 ずらす、上限を変える |
| 条件の否定 | 分岐を反転する、常に真・偽にする |
| 例外の扱い | 握りつぶす、別の値に包み直す、一部だけ握る |
| 入力の種類 | 空、`undefined`、不正値、正常値のそれぞれで分岐が変わるか |
| 単位・時刻 | 単位の取り違え、分や秒の無視、タイムゾーン |
| 「相手側」 | 検査対象を呼ぶ側、参照する側 |
| 落ちないのが正解 | 無関係な箇所（ハーネスの確認） |

### 4. 見逃し

- 守ると言っている状態のうち、テストが無いもの（`undefined`・負の値・`NaN`、障害時、別の分岐）
- **同じ関数の別の呼び出し元**を grep し、その経路のテストを見る
- 仕様の表がある場合は、値を 1 つずつ実装と照合する
- **モックで通るテストは、モックが実際の経路を再現しているかを、実物のライブラリを通して確かめる**（#387: モックは生の `Error` を投げたが、実際の next-auth は `CallbackRouteError` に包んで返した）。変異が全て落ちても、この種のずれは見つからない

### 5. テストの質

`docs/guides/testing-policy.md` 3節の兆候で見る。そのほかに次を確かめる。
- スナップショット（`toMatchSnapshot`）の追加・`-u` での更新は、いまの出力を期待値にしている（4節）
- 名前と中身のずれ（「障害を守る」と言いながら、モックの戻り値を見ているだけ、など）
- 合算の期待値（`windScore + 20`）。落ちたときに原因を絞れるか
- 非同期: `.resolves` / `.rejects` の `await` 漏れ（vitest 5 はエラーにする）、fake timers の進め忘れ、`Date.now` の未固定
- 独立性: `npx vitest run <ディレクトリ> --sequence.shuffle` を数回流す。実行順に頼るテストは、何回かに 1 度落ちる

### 6. 結論

**マージしてよい**（穴は別 issue に回せる）／**直してからマージ**（仕様とずれている、守ると言った状態が守られていない）／**マージしない**（退行を検知しない、前提が誤っている）のどれかを、理由とともに書く。

## 注意

- **独立した検証をするときは、実装者とも自分とも別の新しいエージェント（できれば別モデル）に、結果を共有せず同じ検証をさせる。** 仕様と差分と手順だけを渡し、先の報告や自分の結論は渡さない。食い違いは、原因を実行で確かめるまで、どちらが正しいとも決めない。依頼文には `pr-verifier` の「守ること」に従うと書く

## 出力の形（固定）

PR（PR でなければ対象のファイル）ごとに、次の順で、日本語で書く。全文をチャットに出す。複数あるときは、先頭に `| PR | 結論 | 理由を 1 行 |` の表を置く。

```markdown
## PR #<番号>（<題名>）

### 保証していること
- <テスト名または観点>: <守る振る舞いを 1 行>

### 変異の表
| 変異 | 結果 |
|---|---|
| <何をどう壊したか> | 落ちた / 生き残った（等価: <根拠>）/ 生き残った（穴） |

### 穴
1. <守ると言っているのにテストが無いもの。落とす入力の案>

### テストの質
- <兆候と該当箇所。期待値の根拠が辿れないもの。無ければ「なし」>

### 仕様の表との照合（表がある場合）
| 仕様の値 | 実装 | 一致 |
|---|---|---|

### 結論
<マージしてよい / 直してからマージ / マージしない>。理由。
- 実行して確かめたこと: <develop に重ねた結果、変異の件数、実物での確認など>
- 確かめていないこと: <範囲。コード読みを「確認した」と書かない>
- 後始末: worktree を削除し、`git status` が clean
```
