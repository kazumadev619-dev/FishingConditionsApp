# test-review

`docs/guides/testing-policy.md` は、テストを**書くとき**の方針である。この skill は、書かれたあとのテストを**別のエージェントや人が検証する**手順を定める。Green は正しさの証明ではないので、実装を壊して落ちることと、守ると言った状態に穴がないことを、実行して確かめる。

- 変異の入れ方と判定の読み方は [`mutation-test`](../mutation-test/SKILL.md) に従う。ここには書かない
- テストの質の基準（兆候チェックリスト、期待値の出どころ、モックの扱い）は `docs/guides/testing-policy.md` の3〜5節に従う

## 検証役の約束

- **コードの修正、push、PR へのコメントはしない。** 読み取りと、一時的な変更だけをする。直す案は報告に書く
- 一時 worktree で作業し、終わったら worktree と取り込んだ ref を消す。**手元の変更は必ず戻し、`git status` が clean と確かめてから報告する**
- シークレットの値は読まない、出さない

## 手順

### 1. PR を取り込む

一時 worktree に PR を取り込み、`npm ci` する。そのうえで**最新の `develop` に重ねても通るか**を見る（PR 上の CI は古い `develop` の上で走っている）。重ねた状態で、関連のテストと型検査が通ることを確かめる。

### 2. 何を保証するテストか

追加・変更されたテストごとに、**守っている振る舞いを 1 行**で書く。PR 本文と、根拠の issue・仕様と突き合わせる。次のものは、その場で書き留める。
- 保証が PR の主張より狭い、または広い
- 期待値の根拠（issue、ADR、`docs/reference/`）が、テスト名かコメントから辿れない

### 3. 変異テスト

`mutation-test` の spec にまとめて流す。変異の観点:

| 観点 | 例 |
|---|---|
| 境界値 | しきい値の「ちょうど」「直上」「直下」 |
| 比較演算子 | `<=` と `<`、`>=` と `>` |
| 点数・定数 | 各点数を 1 ずらす、上限を変える |
| 条件の否定 | 分岐の条件を反転する、常に真・偽にする |
| 例外の扱い | 握りつぶす、別の値に包み直す、一部だけ握る |
| 入力の種類 | 空、`undefined`、不正値、正常値のそれぞれで分岐が変わるか |
| 単位・時刻 | 単位の取り違え、分や秒の無視、タイムゾーン |
| 「相手側」 | 検査対象を呼ぶ側、参照する側 |
| 落ちないのが正解 | コメントや無関係な箇所（ハーネスの確認） |

**PR 本文に書かれた変異テストの結果は、そのまま信じず、再実行する。**

### 4. 見逃し

- 守ると言っている状態のうち、テストが無いものを挙げる（`undefined`・負の値・`NaN`、DB 障害、別の分岐）
- **同じ関数の別の呼び出し元**を grep し、そちらの経路にテストがあるか見る
- 仕様の表がある場合は、**表の値を 1 つずつ実装と照合する**（一覧にして、一致・不一致を書く）

### 5. テストの質

`docs/guides/testing-policy.md` 3節の兆候チェックリストで見る。特に次を確かめる。
- トートロジー（期待値が実装の式や現在の出力の写し）
- モックが多く、守っているのが 1 行だけのテスト
- 名前と中身が合っていない（「障害を守る」と言いながら、モックの戻り値を確かめているだけ、など）
- 合算の期待値（`windScore + 20` など）。落ちたときに原因を絞れるか

### 6. 結論

次のどれかを選ぶ。理由と、直す場合は直す点を書く。
- **マージしてよい**（穴は別 issue に回せる程度）
- **直してからマージ**（仕様とずれている、守ると言った状態が守られていない）
- **マージしない**（テストが退行を検知しない、前提が誤っている）

## 落とし穴

- **変異は、テストファイル 1 つではなく、関連するテスト全体（ディレクトリ単位）で流す。** 1 ファイルだけで流して「生き残った」に見えた変異を、別のテストが落とすことがある。実例（#377）: 潮汐の「分を無視する」変異は `tideScore.test.ts` だけでは生き残ったが、`npx vitest run src/lib/scoring/` で流すと既存の `timeZone.test.ts` が落とした。単体で生き残ったら、先にディレクトリ単位で流し直す
- **一時 worktree の中で、その worktree の `mutate.py` を流す。** `edits` の `file` は実行したときのカレントディレクトリからの相対パスで、spec の `cwd` は `command` の実行先だけを変える。リポジトリ側から流すと、変異は元のリポジトリの実装に入り、テストは worktree で走って、全件が「生き残った」になる（ハーネスの警告「全件が変異なしと同じ結果」が出る）
- **生き残った変異は、等価なものとテストの穴に分け、根拠を書く。** 等価の例: 上限 35 を 36 にしても、満点が 15+12+8=35 なので結果が変わらない。`<=2` を `<2` にしても、2 時間で式の値が連続していて変わらない。根拠なしに「等価」としない。穴なら、落とすテストの入力を 1 つ書く
- **モックで通るテストは、モックが実際の経路を再現しているかを、実物のライブラリを通して確かめる。** 実例（#387）: モックは生の `Error` を投げたが、実際の next-auth は DB 障害を `CallbackRouteError` に包んで返した。「障害をそのまま投げる」という仕様の例が成り立っていなかった。テストは緑でも、守る状態は守られていない。変異が全て落ちても、この種のずれは見つからない
- **実行して確かめたことと、確かめていないことを分けて報告する。** 「コード読みでは同じはず」を「確認した」と書かない。未確認の範囲（ブラウザでの見え方、別のコールバック内の障害など）は明記する
- **別モデルによる独立した検証をするときは、Claude の別モデルに、結果を共有せず同じ検証をさせる。** 仕様と差分と手順だけを渡し、先に出た報告や自分の結論は渡さない（渡すと同じ見落としを共有する）。2 つの報告の食い違いを突き合わせる。食い違いは、原因を実行で確かめるまで、どちらが正しいとも決めない（例: 分の変異の食い違いは、流した範囲の違いが原因だった）。Codex は使わない。依頼は `orca-cli` で送る
- **検証の依頼文には、守ることを書く。** コードの修正・push・コメントをしないこと、変更を戻して `git status` が clean と確かめること、シークレットの値を出さないこと

## 出力の形（固定）

PR ごとに、次の順で、日本語で書く。全文をチャットに出す（ファイルに置くだけで終わらない）。

```markdown
## PR #<番号>（<題名>）

### 保証していること
- <テスト名または観点>: <守る振る舞いを 1 行>

### 変異の表
| 変異 | 結果 |
|---|---|
| <何をどう壊したか> | 落ちた / 生き残った（等価: <根拠>）/ 生き残った（穴） |

### 穴
1. <守ると言っているのにテストが無いもの。落とす入力の案>

### 結論
<マージしてよい / 直してからマージ / マージしない>。理由。
- 実行して確かめたこと: <develop に重ねた結果、変異の件数、実物での確認など>
- 確かめていないこと: <範囲>
- 後始末: worktree を削除し、`git status` が clean
```

複数の PR があるときは、先頭に PR ごとの結論の表を置く。
